Cloudflare Pages custom domains: verify deployment and duplicate URLs

By KYD Editorial · First published 2026-07-12 · Last editorial review 2026-10-05

English edition adapted on 2026-10-05. The original source-check date is retained below; this is not a fresh product or match investigation.

A connected-domain badge does not prove that every path serves the intended file. Separate the registrar, DNS, Pages project and deployment output, then test actual responses.

Four responsibilities, not one

The registrar manages domain ownership and renewal. Authoritative DNS directs hostnames. The Pages project chooses the repository, branch and build output to publish. The deployed files supply the content. Gabia was a registrar example in the original guide, not a verified claim about KYD’s registrar.

  1. Confirm the intended page works at the Pages deployment URL before investigating the domain.
  2. Add each intended hostname under the project’s Custom domains.
  3. Follow Cloudflare’s conditions for root domains or subdomains using external DNS.
  4. Preserve email and other service records before changing delegation.
  5. Once association and certificates are ready, test HTTPS and the canonical destination with real requests.

KYD’s actual duplicate-path observation

Before correction on September 6, 2026, the following paths returned duplicate content. These are observations of public HTTP responses, not a review of every Cloudflare setting or another project’s configuration.

PathBefore correctionIntended behavior
/Homepage, 200Canonical homepage
/public/The same homepage, 200Permanent redirect to /
/posts/windows-file-extension/Article, 200Canonical article
/public/posts/windows-file-extension/The same article, 200Permanent redirect without /public

After deployment on September 7, /public/ returned 301 to /, and the duplicate article returned 301 to its equivalent /posts/ path. Both destinations returned 200. /blog redirected to /posts/ with 301, while an arbitrary missing path returned 404. Comparing the same paths before and after established that those rules were actually applied.

Publish redirects in the deployment output

The repository held equivalent files in the root and public folders. Publishing the root could expose public as a second web path. Choose the intended output folder and address any already-public duplicates. For this static Pages case, the deployed _redirects file included:

/public / 301
/public/* /:splat 301

The wildcard preserves each article’s remaining path rather than sending everything to the homepage. A generic local HTTP server does not execute Cloudflare’s redirect rules. Routes handled by Pages Functions may need separate handling; review the official scope.

Check six things after connecting

  • HTTP redirects to the intended HTTPS address.
  • Root and www converge on one canonical host.
  • Article URLs work directly and after a reload.
  • Missing pages return an actual 404, not just an error-looking page with 200.
  • robots.txt, sitemap.xml and verification files are not replaced with homepage HTML.
  • Folder prefixes and old URLs resolve consistently with the canonical tag.

A canonical tag is a preferred-URL signal; a 301 moves a request. Adding the tag does not remove duplicate public paths.

When a new deployment looks old

Compare the GitHub commit, production deployment commit and changed sentence in the public HTML. Do not repeatedly change DNS before checking deployment status. The response and cache guide explains how to distinguish these causes.
