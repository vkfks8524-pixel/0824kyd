Website changes not showing? Check the response before clearing data

By KYD Editorial · First published 2026-07-12 · Last editorial review 2026-10-05

English edition adapted on 2026-10-05. The original source-check date is retained below; this is not a fresh product or match investigation.

An old-looking page is not automatically a cache problem. Compare the URL, deployed HTML and stylesheet first so that you do not erase logins or offline work unnecessarily.

Start with one URL and one visible change

Copy the complete address, including the host and path. A www address, a different signed-in account or a different language setting can legitimately show another page. Choose one changed sentence or button label as the evidence to compare, rather than relying on an impression that the design looks different.

Another device also gets the old sentenceProduction commit, output folder and domain targetWhether both requests passed through the same CDN cache

Reloading is different from deleting data

In Chrome or Edge on Windows, try a normal reload and then Ctrl + Shift + R. A private window provides another comparison, but changes account and extension conditions; it does not clear the server or CDN cache. If clearing cached images and files is necessary, inspect the selected boxes. Cookies, site data and saved passwords are separate categories. Export or save offline drafts before deleting a web app’s site data.

For site owners: inspect Network responses

  1. Open the browser’s developer tools, select Network and reload.
  2. Record the document’s Request URL and status, including its final redirected address.
  3. Search the Response for your changed sentence. If the response is new but the screen is old, inspect client rendering, service workers and account-specific state.
  4. Inspect the stylesheet separately: compare its URL and content with the deployed CSS.
  5. While developer tools remain open, use Disable cache for a controlled comparison, then restore the setting.

A 304 Not Modified response permits reuse after validation; it is not proof of an error or an outdated file. A 200 response is not proof that the latest commit was served either. Compare content as well as status.

KYD’s documented duplicate-path case

On September 6, 2026, both / and /public/ returned 200 with the same homepage title. /public/posts/windows-file-extension/ also exposed the original article. The repository maintained deployment files in both the root and public folders, so publishing the root exposed two paths. Clearing browser data could not fix this duplication: the correction was a deployed redirect from /public/* to the equivalent canonical path. See the Cloudflare Pages domain and duplicate-path guide.

CSS versions are useful, not magic

A content-hashed filename such as style.a1b2.css is an illustrative way to make new HTML request a new stylesheet. You must update the HTML reference too. Adding ?v=2 depends on the server or CDN cache-key configuration and is not a guaranteed bypass. Before a CDN purge, review the affected URL scope in the service’s official dashboard.

What counts as resolution?

Record the intended sentence and stylesheet from the production domain, then compare a fresh browser session. When requesting help, provide the full URL, check time, expected and actual text, and deployment commit. Do not publish raw network logs that may contain login cookies.
