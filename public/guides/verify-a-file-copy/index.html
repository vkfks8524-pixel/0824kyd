02 / Verify a copy

How to verify a copied photo file—and understand a mismatch

Use a local byte comparison, interpret SHA-256 fingerprints, and distinguish a failed copy from an edited or converted photo export.

Published and reviewed October 7, 2026 · KYD · 7 minute guide

In this guide
  1. A copy check answers one narrow question
  2. A small, repeatable comparison
  3. Interpret the result without jumping to a conclusion
  4. Try a known result before selecting personal files
  5. Where this check stops

A copy check answers one narrow question

Two files can show the same photograph without containing the same bytes. One might be a resized JPEG, the other an original HEIC. Conversely, two byte-identical copies can both contain a damaged original. Decide which question you want to answer before choosing a test.

The KYD file copy checker answers: are these two selected files byte-for-byte identical? It reads them locally, compares every byte and displays a SHA-256 fingerprint for each. It does not upload, decode, repair or delete them. It does not scan a folder, inspect your cloud account or authenticate the person who created a file.

A small, repeatable comparison

  1. Keep the source untouched. Copy it to a different location using your normal file-copy method.
  2. Wait for the copy operation to finish. Make sure both are actual downloaded files rather than cloud placeholders.
  3. Select the source as File A and the copied file as File B in the checker. The tool accepts files up to 32 MiB each.
  4. Run the comparison. Record the result and the two fingerprints locally if needed.
  5. Open the copied image in a trusted viewer. For a video, also check playback and audio. A byte comparison is not a media-decoding test.

The file picker only grants this page access to the files you choose. Cloud-backed file pickers may themselves download a file through the operating system before the browser can read it. That is different from this tool uploading anything. If you need to avoid that download, choose files already saved locally.

Interpret the result without jumping to a conclusion

ResultWhat it establishesNext step
Byte-identicalThe selected contents match at the time of reading. Names and timestamps are not compared.Open the copy. Keep checking the rest of the collection and independence of storage.
Different byte sizesThese are not identical copies.Check whether you selected an original versus an export, edit or thumbnail.
Same size, different bytesSize alone would have missed the difference.Compare export settings and repeat a plain copy into a new folder.
Unable to read / too largeNo comparison was completed.Leave the originals alone. Use an appropriate trusted desktop verification tool for larger files.

Google Photos Storage saver can compress or change a file’s format. Apple also distinguishes exporting originals from other ways of saving photos. A mismatch after conversion is not, by itself, evidence of corruption. If your goal is to preserve the camera original, compare unmodified originals rather than a rendered edit. Keep a useful edited version as an additional item if you want both.

Try a known result before selecting personal files

The checker has a built-in demonstration using three tiny text byte sequences, not photos. It compares abc with another abc, then with abd. The first pair must match. The second pair must differ even though both files are three bytes long.

The expected SHA-256 for the UTF-8 bytes of abc, with no newline, is:

ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad

This fixture catches a particularly bad implementation: declaring two files equal because their names or sizes match. KYD’s direct comparison checks contents; the fingerprint is also useful as a record you can compare later. A fingerprint has no built-in proof of origin—an untrusted file accompanied by an untrusted fingerprint is still untrusted.

Where this check stops

One match does not inventory a whole library, preserve album membership or confirm account recovery. Live or motion photos can involve more than a single still-image file; companion media and metadata need their own checks. Do not treat selecting one exported JPEG as a test of every component.

The browser digest API reads whole inputs into memory, so this implementation caps each file at 32 MiB. It deliberately avoids promising multi-gigabyte video verification. For a collection, maintain a manifest and use a suitable batch verification workflow; do not laboriously rename hundreds of originals to fit a two-file tool.

After a successful copy comparison, test the broader recovery path using the recovery drill. A copy that cannot be found, opened or accessed without a lost device is not yet a useful recovery plan.
