Verify a copied photo file: a repeatable experiment and mismatch guide

Download five controlled image files, reproduce byte comparisons, and separate a failed copy from a metadata change or an unreadable image. Includes hashes and next steps.

A matching picture is not necessarily a matching file

To verify a plain file copy, compare its contents and then open the copy. These answer separate questions. Byte equality establishes that the selected contents match; opening checks whether a viewer can use them. Neither step inventories a whole photo library.

This guide includes a controlled experiment you can repeat without selecting personal files. We created five small SVG image files with precisely defined changes. You can inspect the source, download the exact bytes, compare the fingerprints and run the same pairs in the local checker.

What this evidence covers: software behavior on synthetic image files. These graphics are not camera photos. SVG metadata is not EXIF; no Apple or Google export, failing drive, JPEG/HEIC decoder or personal photo collection was tested by this experiment.

Five files that expose four common assumptions

Original KYD SVG test graphics, not camera photos. The first two use identical drawing instructions; only their metadata differs. No third-party image is used.

The reference is a 640 × 400 geometric SVG with a small metadata value. It contains no scripts, external resources or private information. The exact copy retains every byte. One variant changes only the metadata value; another changes one color character. Both preserve the reference’s byte count. The truncated variant retains only the first 200 bytes.

We use five pairs, including the deliberately broken file against itself. Expected outcomes follow from the construction of the files, not from trusting the checker’s verdict:

The important contrast: the metadata-only variant keeps the drawing instructions unchanged but must fail a byte-equality test. Meanwhile, two copies of the truncated input must pass that test despite having incomplete image markup. “Different” does not diagnose corruption, and “identical” does not certify image health.

Boundaries: this was one browser environment. The file-picker test used generated local files, not a browser download-and-reselect round trip. It does not establish mobile-device compatibility or behavior for camera formats. Read the machine-readable observation record and repeat the experiment yourself.

Repeat the experiment with or without downloading

Route A: run the built-in image cases

  1. Open the image-file experiment. Choose one of the five named case buttons.
  2. Read the pair names, byte counts, computed result and reference-check message. The page calculates the result from embedded copies of the same public fixture bytes; it does not read your selected personal files.
  3. Expand the fingerprints and compare them with the published reference list. Run the broken-input pair as well as the successful-copy pair.

Route B: repeat through the ordinary file pickers

Download the reference and the variant you want below. Use the download links, not “save webpage,” which may wrap or rewrite a document. If your browser opens the SVG instead, save the linked file without editing its contents. First check its byte count and fingerprint.

  • reference.svg — 458 bytes. Original geometric test chart.
  • identical-copy.svg — 458 bytes. Exact copy; only the filename is different.
  • metadata-change.svg — 458 bytes. One metadata byte changed. Drawing instructions unchanged.
  • visible-change.svg — 458 bytes. One color byte changed; same byte count, different drawing.
  • truncated.svg — 200 bytes. Only the first 200 bytes retained; deliberately incomplete XML.

Download SHA-256 reference list · Machine-readable manifest

  1. In the checker’s File A field, select the downloaded reference. In File B, select a variant.
  2. Choose Compare files. Compare the observed size, result and hashes with the table and reference list.
  3. For the last case, select truncated.svg in both fields. Expect byte equality, not a repaired image.
  4. If a result differs from the reference, stop. Check whether you saved the SVG file itself or a browser-generated HTML page, then download a fresh copy. Do not experiment on your only personal original.

The fixtures are original KYD teaching files. You may reuse, modify and redistribute them for testing with attribution to this guide; clearly label modified versions. A reference hash supplied by the same publisher is useful for detecting an altered download, not independent proof that the publisher is trustworthy.

Check the reference without this website’s calculator

For example, in PowerShell opened in your downloaded sample folder, this read-only command prints a SHA-256 digest:

Get-FileHash -Algorithm SHA256 -LiteralPath ./reference.svg

The expected reference size is 458 bytes, and its SHA-256 is:

e07762ee42804677d7ebefe867a4fda1a75ab24202c83b00f2cf0a60ff69cf5c

Uppercase versus lowercase hexadecimal letters do not change the digest. Reference hashes were generated using Node’s crypto implementation, separately from the browser’s Web Crypto calculation. The fixture generator documents every change.

Now compare a real copy without changing the source

Choose a source that is already readable and locally available, then make an ordinary copy into a new folder. Wait until copying finishes. Do not overwrite a previous backup during this test. Compare the source with that copy, not an original with a resized sharing export.

Apple documents multiple ways to archive or copy iCloud information. Record which export route you used. An unmodified-original download and a rendered or converted version are different comparison targets. Keeping both may meet your needs better than declaring one corrupt.

A short mismatch investigation

  1. Confirm the target. Are you checking a plain copy, an edited derivative or a cloud export? Write that down before interpreting the result.
  2. Check local availability. A cloud-backed picker may download an item before the tool reads it. Choose files already stored locally if you want to isolate a disk-to-disk copy check.
  3. Repeat narrowly. Copy one readable source into a fresh folder. Compare that pair. If it matches but an earlier export differs, investigate the export settings rather than blaming the copying method.
  4. Preserve an unresolved result. Keep both files and a private note of the workflow. Do not rename a variant over the source to make a discrepancy disappear.
  5. Stop on hardware symptoms. If a drive disconnects or repeatedly reports read errors, stop repeated experiments and seek suitable recovery assistance. This browser tool cannot diagnose or repair a drive.

Saving the checker’s text result omits filenames but includes fingerprints and sizes; keep it private. The new on-screen next step depends on the actual result, including a warning for empty matching inputs. It is not a “safe to delete” instruction.

The small text self-test is still available

The original Try known demo button compares the UTF-8 bytes of abc against abc, then against abd. The first pair matches and the second differs despite both being three bytes. The SHA-256 reference for abc, with no newline, is:

ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad

This is a useful quick self-test. The image fixtures add the distinction that a byte-level test cannot infer whether the drawing changed or the file still decodes. A text-only self-test did not establish those viewer outcomes.

What remains outside the experiment

The checker reads the selected bytes in memory, compares them directly and separately calculates SHA-256. It does not upload, decode, repair, scan for malware or delete files. MDN notes that the browser digest API needs the whole input in memory and a secure context; the 32 MiB-per-file limit is intentional.

One successful pair is not a complete-library audit. Our experiment does not check album membership, original capture dates, cloud account access or Live Photo pairing. For motion components, continue with the Live Photo component guide. For a collection, use an appropriate batch inventory and verification workflow rather than extrapolating from one pair.

After checking copies, follow the non-destructive recovery drill to test retrieval from the destination you intend to rely on. Preserve your originals until the wider plan is verified.
